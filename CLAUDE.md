## Stack
- Next.js (App Router) + TypeScript, deployed on Vercel (auto-deploy from `main`, previews on PRs)
- Styling: plain CSS ported from the prototype (`app/globals.css` + CSS Modules). No Tailwind, no UI kit.
- Fonts: Geist + Geist Mono via `next/font/google`
- Hero animation: a `"use client"` component wrapping the prototype's canvas code (no three.js needed)
- Database (phase 1): Postgres via the Vercel Marketplace (Neon), accessed with Drizzle ORM (`lib/db/`)
- Migrations: `npm run db:generate` creates SQL in `drizzle/`; `npm run build` runs `drizzle-kit migrate` (never `push`) before `next build`, so each Vercel deployment migrates its own database (preview → its Neon branch, production → main). Locally without `DATABASE_URL` the step is skipped.
- No local database and no Vercel CLI in Codespaces. Verify database features on the preview deployment only.
- Next 16: auth for `/admin` lives in `proxy.ts` (the renamed middleware).
- /admin renders per request, never prerendered (round 18). With `cacheComponents` and `partialPrefetching`, prefetch prerenders could start the session lookup and have its Neon fetch cut off when the prerender ended ("During prerendering, fetch() rejects…", reported as "session lookup failed" on /admin/contacts). So `app/admin/layout.tsx` sets `instant = false` (no static shell), `prefetch = "force-disabled"` and awaits `connection()` first; `sessionSubject` (admin and member sessions) awaits `connection()` first, before the cookie's expiry check (`Date.now()` in `readSession`; round 20, after production logged "Date.now() while prerendering" on every admin page) and the query; and its catch, like `roleFor`'s, calls `unstable_rethrow` so Next.js control-flow errors are never reported as failures. The build lists every /admin page as ƒ except the two `[id]` routes under /admin/events, whose ◐ is the fallback shell Next always builds for a dynamic param (it's empty: every /admin HTML shell is 0 bytes). Keep new admin pages under this layout.
- Domain stays registered at Wix; DNS will point to Vercel later. Don't build anything on Wix.

## Invites to contacts (round 12)
Rules, enforced in code (`lib/invites.ts`):
- Eligible: a contact with a valid email, not linked to a member, not suppressed and never invited. Each contact is invited at most once, ever: `contacts.invited_at` is set on send and never reset.
- Suppression list `invite_suppressions` (email_hash unique, reason unsubscribe | bounce | complaint, created_at). The hash is SHA-256 of "nyubs-suppress:" + the lowercased, trimmed address, deliberately unkeyed, so a rotated secret can never forget who opted out; the same expression runs in SQL (`hashSql`). A re-imported contact is still recognised.
- Anyone who unsubscribes from an invite, hard-bounces or complains is added and never invited again. Bounces and complaints also block every other email (`undeliverable()` in `sendEmail` / `sendBatch`, which skip them). An invite unsubscribe only stops invites: if that person joins later, that's their own choice.
- Bounces and complaints arrive by Resend's webhook, `POST /api/resend/webhook` (events `email.bounced` and `email.complained`), verified the Svix way with `RESEND_WEBHOOK_SECRET` (whsec_…; unsigned, bad or older-than-5-minutes requests get a 401). Nothing else from the webhook is stored.
- Invites are super admin only on the server; admins see invite status read-only. Sending is blocked until a postal address is set.
- `/admin/contacts/invite` (super admin; "Invite" button on Contacts, no nav tab):
  - Recipients: pick a source (each with its eligible count) and optionally an upcoming published event to feature.
  - Compose: subject, message (blank line = paragraph, `{first_name}`) and the footer reason, prefilled from `DEFAULT_INVITE`, with a live preview (`previewInvite`, sandboxed iframe).
  - "Send a test to me" is required: a real send needs a test of exactly the same invite (subject, message, reason, featured event; `inviteHash`) in the last 24 hours, and the eligible count the admin confirmed. Real sends only in production (previews hold copies of real contacts). Postal address required for tests and sends.
  - Server actions (`app/admin/contacts/invite/actions.ts`) all go through `requireSuperOr403`.
- Invite queue (`lib/invite-queue.ts`), tables `invite_campaigns` and `invite_queue`:
  - `invite_campaigns`: status test | queued | paused | done; source, event_id, subject, body, reason, content_hash, total, created_by.
  - `invite_queue`: campaign_id, contact_id **unique**, so a contact is in one campaign ever; status queued → sending → sent | failed, or skipped; sent_at.
  - "Send" queues every eligible contact of that source and sends today's share at once (`after()`). Each run sends up to what's left of the shared daily limit (`EMAIL_DAILY_LIMIT`, rolling 24 hours, shared with welcome emails, sign-in links and announcements) minus `INVITE_RESERVE` = 10 kept for sign-in links and welcome emails.
  - Rows are claimed atomically (`update … where id in (select … for update skip locked)`), so overlapping runs never double-send. Each contact is re-checked for eligibility at its turn (otherwise skipped). Batches of 100. `invited_at` is set after a successful batch. A failed batch is marked failed and never retried automatically (no risk of a double invite).
  - The rest goes out from the Vercel cron `GET /api/cron/invites` (vercel.json: 15:00 and 03:00 UTC). Two runs 12 hours apart, because the limit is a rolling 24 hours: a run at the same time each day could still see yesterday's batch. It needs `CRON_SECRET` (Vercel sends it as a bearer token; without it the route refuses).
  - The campaigns table shows queued / sent / failed / skipped per campaign with Pause / Resume.
  - Logged: `invite.test`, `invite.campaign`, `invite.batch` (every batch, actor "system" from runs), `invite.pause`, `invite.resume`, `invite.run`.
- The invite email (`lib/invite-email.ts`): from "NYU Blockchain Society <hello@nyublockchainsociety.com>", reply-to as other emails, the usual template (HTML and text), heading "Add your block". Default copy (editable per campaign): subject "An invitation to NYU Blockchain Society"; "Hi {first_name}," (the contact's first name, else "there"); they registered for the 2024 NYU Blockchain Conference at New York University; the one-liner; an invitation to add their block. A featured event adds "Coming up: <title>, <date and time ET>, <venue>. Members get the invite first." Footer: the editable reason ("You registered for the 2024 NYU Blockchain Conference.") plus "This is a one-time invitation: we won't email you again unless you join.", an unsubscribe link, one-click List-Unsubscribe headers and the postal address.
- Invite tokens are encrypted with `seal`, so a link shows no id or other data:
  - The join token (`i.<contact id>.<expiry>`, 60 days) rides on the "Add your block" button: `/?join=1&src=invite-<source>&invite=<token>` (the source is cut to the 40-character limit). The home page moves it out of the URL into sessionStorage (`nyubs:invite`, `lib/join-source.ts`) at once. The join flow pre-fills the invited address (`inviteEmail`, only for an unused token of an unlinked contact), and `join()` spends it once (`contacts.invite_used_at`, `spendInviteToken` in `lib/invite-join.ts`), linking that contact to the new member even under another address ("auto (invite)", `link_method` 'invite', logged as "system"; never a pair an admin undid).
  - The unsubscribe token (`c.<contact id>`) never expires. `/unsubscribe` and `POST /api/unsubscribe` accept member and contact tokens (`lib/unsubscribe.ts`). A contact's unsubscribe puts the address on the suppression list for good: no "Resubscribe"; the page says "You won't get another invitation".
- Settings (round 12): table `settings` (key primary, value, updated_by, updated_at; `lib/settings.ts`). `/admin/settings` (super-only "Settings" tab, last) edits the society's postal address (`postal_address`, up to 300 characters). Saving is logged as `settings.edit` with old → new. The address shows in the footer of every invite and announcement (`postalAddress` in `renderEmail`); welcome and sign-in emails don't carry it.

## Error monitoring (round 16)
- Sentry via `@sentry/nextjs` (pinned 10.75.3): `instrumentation.ts` (server and edge, `onRequestError` for uncaught errors), `instrumentation-client.ts` (browser), `sentry.server.config.ts`, `sentry.edge.config.ts`, `app/global-error.tsx`; `withSentryConfig` in `next.config.ts`. Off unless `SENTRY_DSN` (server/edge) and `NEXT_PUBLIC_SENTRY_DSN` (browser) are set; nothing breaks without them. Source maps upload only when `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` are all set, and are deleted from the deployment after upload.
- Query parameters never go to Sentry (decided, round 18). A Drizzle "Failed query" error ends with "params: …" (the bound values: emails, token hashes); `scrubText` cuts everything from "params:" on, in every exception of the chain (an error and its causes), the message, breadcrumbs, extra and contexts, and drops any `params` key. The SQL before it (placeholders only) stays. `npm run test:sentry` (`test/sentry.mts`) runs a fake Drizzle error with an email and a token through Sentry's real event pipeline and checks neither survives; run it whenever `lib/sentry-options.ts` changes.
- Privacy (`lib/sentry-options.ts`, shared by all runtimes): `sendDefaultPii: false`, `tracesSampleRate: 0` (errors only), no session replay, no local variables. `beforeSend` drops the user, cookies, headers, request body and query string (keeps only the URL path and method), masks email addresses and token parameters (`t`, `d`, `token`, `invite`, …) in messages, exceptions, breadcrumbs, extra and contexts. Never pass personal data to `reportError`.
- Areas: every handled error goes through `reportError(area, label, e)` (`lib/monitoring.ts`: logs as before and sends to Sentry with tag `area`): join, checkin, live (the live screen's first failed poll per outage), invite, announcements, admin, update, forms (inquiries and accelerator), site. Uncaught errors get their area from the path (`areaForPath`). Failed email sends are reported once, in `lib/email.ts`, with the area of their email kind.
- Test: `/admin/sentry-test` (super admins only, linked from Settings, no tab) sends one server test error (server action, flushed, logged as `sentry.test`) and one browser test error, both tagged `area:admin` and `test:yes`.

- Admin sign-in (round 9): personal logins by email magic link (built in, not Auth.js). `/admin/login` → a link (`auth_tokens`: only a SHA-256 is stored, single-use, 15 minutes) → `/admin/login/verify`, where signing in takes a button click (mail scanners open links and would use them up) → a session cookie `nyubs_admin` (30 days). Security (round 9.1 review):
  - Sessions are server-side (`auth_sessions`, `lib/sessions.ts`): the cookie is a random session id signed with `AUTH_SECRET` (HMAC, `lib/session-token.ts`), the table stores only its SHA-256, and every request checks the row is live. Sign-out revokes the row (a copied cookie stops working too); removing an admin revokes all their sessions; member sessions (`nyubs_member`, 24 hours) work the same way. Cookies: HttpOnly, Secure on Vercel, SameSite=Lax, path /.
  - Magic links: 256-bit random tokens, only the SHA-256 stored, looked up by hash (no plaintext comparison; the attacker can't steer the hash), single-use (marked used in the same statement that reads them), 15 minutes, and a successful sign-in spends every other unused link for that person.
  - Rate limits on both link requests (`/admin/login`, `/update`): per IP (5 per 10 minutes) and per email (3 per 15 minutes, keyed by an HMAC, counted whether or not the email exists).
  - Same response, same timing: both requests return the same message for any valid email; the lookup and the send run after the response (`after()`), so timing can't tell admins or members apart.
  - CSRF: every state-changing admin action is a server action (POST only); Next.js rejects server actions whose Origin doesn't match the host (checked: a forged Origin is aborted), and cookies are SameSite=Lax. The only state-changing route handler is `POST /api/unsubscribe`, authorized by its encrypted token, not cookies. Export routes are read-only GETs.
  - Links are built from a fixed origin (`baseUrl()`: the canonical domain in production, Vercel's own deployment URL env on previews), never from the request's Host header. Only `SUPER_ADMIN_EMAIL` or active `admin_users` can sign in, and the role is re-read on every request (`getAdmin` in `lib/admin.ts`), so removing an admin or changing a role applies at once.
