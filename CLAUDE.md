Maintainer: Fang. Co-leads: two society organizers (names kept out of this public repo).

## Public repo rules
- Never commit secrets: database URLs, passwords, API keys. Use .env.local locally and Vercel environment variables in production. Provide a .env.example with empty values only.
- Never commit member data: no CSVs, Luma exports, spreadsheets, or real names/emails in seed data or tests. Use obviously fake test data (e.g. test@example.com). Local test fixtures (fake imports) live in `fixtures/local/`, which is git-ignored; `*.csv`, `*.tsv`, `*.xlsx`, `*.xls` and `*.xlsm` are ignored everywhere (round 9.1). Checked in round 9.1: no spreadsheet or export file has ever been in git history (all refs and unreachable objects).
- Never put personal contact details of organizers or members in code or docs.

## The spec
`docs/prototype.html` is the approved design. Match it closely: layout, copy, colors, type, motion and the hero interaction. Port it; don't redesign it. When unsure, open it in a browser and compare.

## Stack
- Next.js (App Router) + TypeScript, deployed on Vercel (auto-deploy from `main`, previews on PRs)
- Styling: plain CSS ported from the prototype (`app/globals.css` + CSS Modules). No Tailwind, no UI kit.
- Fonts: Geist + Geist Mono via `next/font/google`
- Hero animation: a `"use client"` component wrapping the prototype's canvas code (no three.js needed)
- Database (phase 1): Postgres via the Vercel Marketplace (Neon), accessed with Drizzle ORM (`lib/db/`)
- Migrations: `npm run db:generate` creates SQL in `drizzle/`; `npm run build` runs `drizzle-kit migrate` (never `push`) before `next build`, so each Vercel deployment migrates its own database (preview → its Neon branch, production → main). Locally without `DATABASE_URL` the step is skipped.
- No local database and no Vercel CLI in Codespaces. Verify database features on the preview deployment only.
- Next 16: auth for `/admin` lives in `proxy.ts` (the renamed middleware).
- Domain stays registered at Wix; DNS will point to Vercel later. Don't build anything on Wix.

## Commands
- Production testing after deploys that touch email, sign-in or members: `docs/testing-checklist.md`.
- `npm run dev`: dev server (Codespaces: open forwarded port 3000)
- `npm run build`: must pass before every commit
- `npm run lint`

## Phase 1 app: "Add your block" (join in the hero)
Built. See "Decided" below for the flow, data model and admin.
- Welcome email (round 9, `sendWelcome` in `lib/member-email.ts`): exactly one, on a new join only (the insert, not a re-submit; never retroactively to existing members), sent with `after()` so it never slows or breaks the join. Subject and heading "Block #<n> added. You're on the chain." (from 50 members; before that "Block added. You're on the chain."), the short boilerplate, the notify line when they came from a notify block, an "Update your block" button (→ `/update`) and an unsubscribe link.
- "Update your block" (round 9, `/update`; footer link and the welcome email): enter an email → the same answer whether or not it's a member → a magic link (purpose `member` in `auth_tokens`, single-use, 15 minutes; never sent to unsubscribed members) → `/update/verify` (a "Continue" click) → a 24-hour signed `nyubs_member` cookie → `/update/edit`, where the member edits their own blocks, notify preferences and optional fields (LinkedIn, role, company, NYU school, grad year, city and country), never name or email. Validation is shared (`lib/member-fields.ts`).
- Unsubscribe (round 9): `members.unsubscribed_at`; unsubscribed members never receive any email (welcome, announcements, magic links). Every member email has a signed, never-expiring unsubscribe link (`/unsubscribe?t=…`, no login) and RFC 8058 headers (`List-Unsubscribe` → `POST /api/unsubscribe`, `List-Unsubscribe-Post: One-Click`), so mail apps unsubscribe in one click. The page itself unsubscribes on one button press, not on load (link scanners open pages; they don't press buttons), and offers "Resubscribe".

## Email (round 9)
- Sent through Resend's HTTP API (`lib/email.ts`, no SDK) from "NYU Blockchain Society <hello@nyublockchainsociety.com>", reply-to `REPLY_TO_EMAIL`. DNS (DKIM, SPF on `send.`, DMARC) is in Wix DNS.
- Secrets live only in Vercel: `RESEND_API_KEY`, `SUPER_ADMIN_EMAIL`, `REPLY_TO_EMAIL`, `AUTH_SECRET`. Never print, log or commit their values.
- One template (`renderEmail`): violet-night header band, white card, system fonts, one violet button; inline styles only (font stacks use single quotes inside `style=""`); always a plain-text version. Admin-written text is escaped.
- `email_log` stores counts only (kind, recipients, time), never addresses or content. Every email counts toward the daily limit (`EMAIL_DAILY_LIMIT`, default 100 for Resend's free plan), checked over a rolling 24 hours. Batches go out 100 per request, spaced 600 ms.
- Links in emails use `baseUrl()` (`lib/base-url.ts`): production → the canonical domain; a preview links to itself, since its tokens live in that preview's database. Without `RESEND_API_KEY` (Codespaces) nothing is sent.

Type and layout

- The pinned story releases exactly when it ends (negative margin on the content layer, not on the pin).
- The HUD ("New York · time ET · Hover a block · drag to rotate") shows only over the hero and fades out on scroll.
- Background: one continuous fixed layer behind ALL public pages (home, /conference, /conference/[year], /media-kit), mounted once by `components/backdrop/Backdrop.tsx` in the `(site)` layout. One canvas (DPR capped at 2), one rAF loop (`backdrop.ts`); sections are transparent so it never stops before the chain or the join section. The network (`network.ts`) is a drifting constellation (nodes, faint edges between near neighbours, small dots travelling along edges) filling the viewport, scrolling with a slow wrapping parallax, with a "blocks forming" cycle: every 3–5 s, 8 nearby nodes ease into an isometric cube, its 12 edges draw one by one with racing dots, a brief glow confirms the block, it holds ~2 s, then relaxes back. A block's nodes are always joined by edges (faint cube edges from the first moment of gathering through the relax, as the network edges they leave fade out) and share one opacity, so there is never a cluster of loose nodes; a block split by the wrap seam hides its nodes. Network nodes, edges and dots are drawn batched by opacity (`batch.ts`). Density (`densityFor`), round 6: base ~140 nodes at 1440×900 scaled by viewport area (phones half); screens ≥1280px wide get +30% nodes (~182 at 1440×900), phones and tablets keep the base; traveling dots are 1.5× the old ratio (base × .19 × 1.5, ~40 at 1440×900); edges reach ~20% further (3.12 node gaps of the base density, max 3 per node) so the web looks more interlinked. Up to 3 formations at once; phones max 1. If frame time has to come down, cut nodes (the ≥1280 bonus first) before dots. Copy marks itself `data-bg="dim"` (mission, proof strip, Focus cards, chain cards, join copy, sub-page text: ~40% less network, soft edge) or `data-bg="clear"` (hero text: stronger); blocks never form there and fade if copy scrolls over them; the network fades only right behind the hero logo (radius 1.7·S) and under an open label; blocks don't form in a ring around the logo (2.4·S). The hero 3D logo (`components/story/field.ts`) is a painter on the same canvas, offset by the pin's position, with a transparent hit layer in the pin for pointer input. The logo is the network's core, not an object on top of it (round 7, `backdrop/core.ts`): same material as the network (lilac nodes and solid lilac edges, only slightly larger and brighter; a glow only on a highlighted block; dots in the network's dot style). Density rises toward it: a halo of extra nodes (~30% of the page's node count, so phones follow the same density rules) between 1.1 and 2.3 logo radii, denser near the logo (~2–3× the page), with short edges (max 3 per node) and its outer nodes tied into the background network. The nearest 8–12 nodes (halo or background) connect straight to the logo's outer (hull) vertices, re-picked every ~280 ms as it rotates and nodes drift, with dots constantly running into and out of the logo (more traffic near the core than elsewhere). Every 10–15 s a block that forms near the logo reaches out to it with a solid edge before it relaxes. No dashed connections anywhere (join trail and member links are solid too). Assemble on load (`field.ts`), once per session (`sessionStorage` "nyubs:assembled"): 20 nodes fly in from nearby network nodes to the cubes' vertices, then the edges draw in (~1.2 s total), then the core connects and the logo rotates as before; skipped under reduced motion and on later loads in the same session (the finished logo shows). Static and dot-free under reduced motion. Keep 60 fps on a mid-range laptop (round 7, headless Chromium with software canvas: ~2.6 ms per frame at 1440×900, ~3.0 ms at 1920×1080, ~1.0 ms at 390×844). Paused when the tab is hidden; static under reduced motion (redrawn only on scroll/resize).

Data and security
- `members`: id serial (= block number), name, email (unique on `lower(email)`), affiliation enum (alumni, industry, student, faculty_staff, friend), blocks text[], notify text[], source, linkedin_url, role, company, school, grad_year, location ("City and country" as entered), country (read from the part after the last comma on save, normalized by `lib/location.ts`: US/UK/UAE spellings and US states count as their country), show_on_wall, wall_name, wall_approved (retired in round 9: kept in the database, never read or written; `memberColumns` in `lib/members-query.ts` leaves them out), created_at, updated_at. `rate_limit_hits` backs rate limiting.
- Re-submitting an existing email updates that row and keeps its block number; the response is identical, so it never reveals whether an email exists. Follow-up "Strengthen" edits for an existing email can only fill empty fields.
- Server actions with zod, a honeypot, a signed minimum-fill-time token, and Postgres rate limiting keyed by an HMAC of the IP. Never store raw IPs. `FORM_SECRET` is optional (falls back to `DATABASE_URL`).
- Without `DATABASE_URL` outside Vercel, the flow shows a clear local-only message instead of failing.
- `contacts` (round 4; round 9.2): id, name (nullable), email (nullable since round 9.2), headline (nullable), source (e.g. 'luma-2024', 'linkedin-2026-10'), checked_in bool nullable, imported_at, invited_at nullable, member_id nullable FK → members (on delete set null), link_method (email | name | manual; null when unlinked). `contact_link_blocks` (contact_id, member_id, actor, created_at; both FKs cascade) holds pairs an admin unlinked. Dedupe: rows with an email on `lower(email)`; rows without one on (lower(name), lower(headline)) (partial unique index). Contacts are NOT members: no block number, never counted as members. A contact without an email can never be emailed and is excluded from every email feature, announcements included (today no email goes to contacts at all; any future invite must filter `email is not null`).
- `linkedin_group_members` was removed in round 9.2: its rows moved into `contacts` (name, headline, source and any manual link; email null; never the group role) and the table and its enum were dropped (migration 0012).
- Never commit member or contact data. Test imports only on a preview deployment with an obviously fake CSV (example.com), then delete those rows.

Admin
- Admin sign-in (round 9): personal logins by email magic link (built in, not Auth.js). `/admin/login` → a link (`auth_tokens`: only a SHA-256 is stored, single-use, 15 minutes) → `/admin/login/verify`, where signing in takes a button click (mail scanners open links and would use them up) → a session cookie `nyubs_admin` (30 days). Security (round 9.1 review):
  - Sessions are server-side (`auth_sessions`, `lib/sessions.ts`): the cookie is a random session id signed with `AUTH_SECRET` (HMAC, `lib/session-token.ts`), the table stores only its SHA-256, and every request checks the row is live. Sign-out revokes the row (a copied cookie stops working too); removing an admin revokes all their sessions; member sessions (`nyubs_member`, 24 hours) work the same way. Cookies: HttpOnly, Secure on Vercel, SameSite=Lax, path /.
  - Magic links: 256-bit random tokens, only the SHA-256 stored, looked up by hash (no plaintext comparison; the attacker can't steer the hash), single-use (marked used in the same statement that reads them), 15 minutes, and a successful sign-in spends every other unused link for that person.
  - Rate limits on both link requests (`/admin/login`, `/update`): per IP (5 per 10 minutes) and per email (3 per 15 minutes, keyed by an HMAC, counted whether or not the email exists).
  - Same response, same timing: both requests return the same message for any valid email; the lookup and the send run after the response (`after()`), so timing can't tell admins or members apart.
  - CSRF: every state-changing admin action is a server action (POST only); Next.js rejects server actions whose Origin doesn't match the host (checked: a forged Origin is aborted), and cookies are SameSite=Lax. The only state-changing route handler is `POST /api/unsubscribe`, authorized by its encrypted token, not cookies. Export routes are read-only GETs.
  - Links are built from a fixed origin (`baseUrl()`: the canonical domain in production, Vercel's own deployment URL env on previews), never from the request's Host header. Only `SUPER_ADMIN_EMAIL` or active `admin_users` can sign in, and the role is re-read on every request (`getAdmin` in `lib/admin.ts`), so removing an admin or changing a role applies at once.
- `SUPER_ADMIN_EMAIL` (Vercel env) is the recovery key: always a super admin, never stored in `admin_users`, can't be added, changed or removed in the UI, and still signs in if `admin_users` is empty or unreadable. Shown masked on `/admin/team`.
- `admin_users`: email (unique on lower(email), stored lowercase), role (`super_admin` | `admin`), added_by, created_at, removed_at (removing sets it; re-adding clears it).
- Permissions are enforced on the server in every page (`Guard`), action and route (`requireAdmin(min)`, `adminForRoute(min)`); hidden buttons are only a convenience. Both roles: view/search members and contacts; edit members; link and unlink contacts; announcements (draft, test, send). Super admin only: contacts imports, every CSV export, `/admin/team`, permanent deletes (members and contacts), boilerplate approval and site settings (today these are code changes in `/content`; any future settings UI is super-only; `/admin/media-kit-preview` is super-only), and the full audit log (`/admin/audit`: admins see only their own actions).
